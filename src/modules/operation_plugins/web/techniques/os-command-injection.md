# OS command and argument injection

## Applicability and prerequisites

An assigned feature invokes a system utility or a captured response suggests server-side command interpretation. Identify the intended operation and accepted argument grammar, authorized test data and an output channel or approved callback host. Agree a strict request/time bound before delay probes. Use HTTP replay, a controlled callback receiver and local payload construction or equivalents. Never assume access to the target shell, local processes or filesystem.

Choose only the assigned branch and obey the operation's scope, identities, rate and state-change constraints. Missing prerequisites stay explicit; a lookup signal is not proof. Equivalent available tools may replace named capabilities.

## Reconnaissance

1. Inspect the assigned feature for utility-like behavior such as conversion or diagnostics, and distinguish shell interpretation from direct argument passing. A utility name or error banner is only a clue.
2. Record the apparent operating-system/quoting assumptions and permitted options. Find a harmless output marker or owner-provided test artifact usable without reading arbitrary files, opening shells or altering services.

## Hypothesis generation

1. From recorded observations design separate shell-metacharacter and argument/option-boundary hypotheses. A correctly quoted single argument can still select a dangerous option; absence of a shell does not settle the latter.
2. Specify an accepted benign operand, an inert marker, a candidate harmless computed marker and an unrelated/escaped control. Require evidence generated by execution, not a marker already present verbatim in the submitted input.
3. If no output channel exists, plan only approved correlated callback or bounded delay comparisons, naming attribution controls and stop conditions. Do not run commands or callbacks during hypothesis design.

## Vulnerability verification

1. Replay the accepted feature with a benign owned operand and observe the intended output. Repeat an inert unusual-character operand to measure validation/error behavior, keeping authentication and processing settings fixed.
2. For a justified shell context, insert one context-appropriate delimiter and a harmless marker-producing expression. Choose a marker assembled or transformed by the interpreter so raw reflection cannot reproduce the expected result. Compare an escaped/inert form and a syntactically invalid form; do not use destructive commands, file reads, shell access or persistence.
3. For argument injection, vary only a recognized benign option or operand boundary whose interpretation would violate the documented input grammar. Compare the same text as a literal operand where possible. Utility help/version output can show option parsing but does not by itself prove RCE or harmful privilege.
4. If using an approved callback, correlate a unique request marker and distinguish the utility's intended network behavior from an extra command invocation. A generic DNS/HTTP lookup alone may be legitimate; require the established command boundary and inert control.
5. If explicitly authorized, compare a short bounded delay with no-delay and syntactically inert controls, randomizing a few repetitions and rechecking the normal baseline. Stop on noise or service degradation. A slow response, reflected delimiter or command-flavored error alone is inconclusive.

## Execution

1. Demonstrate the confirmed command or argument interpretation using one harmless computed marker in the affected processing channel. State the exact capability: shell execution, additional argument or utility option; do not promote one to another.
2. Remove test input/output objects through normal application operations, close callback listeners and restore job settings. Confirm the ordinary feature completes normally and no queued test job remains active.

## Analysis

1. Compare generated output and controls to exclude input reflection, server-side template evaluation, URL fetching by the intended utility and generic validation changes.
2. Explain shell/OS differences, quote context, option parsing, asynchronous processing and shared worker noise. Successful intended utility execution is not injection, and failure of one delimiter does not establish argument safety.

## Evidence requirements

Retain exact operand/delimiter encoding, expected grammar, accepted output, generated-marker derivation, escaped/invalid controls and repeats. For asynchronous jobs connect job IDs to outputs; for callbacks preserve correlated receiver data and rule out browser-origin requests.

## Limitations

This is a bounded interpretation method, not a shell, file-exfiltration or post-exploitation procedure. Missing safe observability or uncertain utility context leaves the branch untested. Delay and outbound checks require explicit operational bounds.
