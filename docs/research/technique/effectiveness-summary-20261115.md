# Technique experiment effectiveness

## Decision

Expect better formatting and fewer avoidable controller/contract failures. There is narrow evidence
that guidance helps preserve uncertainty when policy is missing. Broader authorship quality,
production task benefit and increased voluntary use are not established.

The experimental task harness differed from production finalization instructions. Its observed
Markdown failure must not be presented as a demonstrated production regression. The later
format-alignment check succeeded once; it does not retroactively repair the earlier result.

A subsequent [production executor-core pilot](production-executor-20261115/README.md) completed
both tested cases correctly with and without lookup. Both lookup-enabled executors voluntarily
consulted the frozen guide, but no classification benefit appeared (17 requests with lookup,
14 without). This establishes curated consultation rather than catalog-search quality or an
increased adoption rate. It exercises production agent construction, run loop, outcome hooks
and SQLite acceptance, with fixture I/O and isolated runtime resources; whole controller
scheduling and model evaluation remain outside that pilot.

## Evidence by question

| Question | Observation | Practical limit |
| --- | --- | --- |
| Does planning become more coherent? | Three focused requests reached cohesive accepted plans after separating policy and data | Planning-only sample; no controlled delivery estimate |
| Can publication consume source evidence? | Matched synthetic supported/contradictory controls were accepted/rejected correctly | Two controls, not broad source-grounding reliability |
| Is authorship easier to consume? | Line-oriented output produced readable Markdown in all three author checks and all three later pipeline documents | Formatting does not establish correct procedures |
| Can generation/publication finish? | Later frozen-source network, filesystem and HTTP cases all completed | Conditional pipeline yield; HTTP retained a demonstrated false-negative rule |
| Does guidance improve easy tasks? | Explicit-policy tasks were correct 6/6 per arm; guidance used 38 requests versus 24 | No accuracy gain; request count is not monetary or token cost |
| Does guidance help with uncertainty? | Discoverable-context primary study: guidance 3/3, no guidance 2/3; only the unavailable-policy case differed | Three synthetic pairs, one run per arm/case |
| Does the uncertainty result repeat? | Exploratory no-guidance run again claimed a violation; guidance text was inconclusive but invalid JSON | The guidance run remains unresolved by the predefined contract |
| Is the formatting failure understood? | Harness omitted production's model-facing JSON contract; one fresh aligned run completed correctly | Plausible contributor, not a controlled causal attribution |
| Are techniques used more often in operations? | Not measured: guidance was supplied directly to task agents | Retrieval, voluntary adoption and continued use require production-path observation |

These studies have different scopes, budgets and instructions. Their outcomes are not pooled into
one accuracy or reliability estimate. Human-accepted useful-document yield remains unknown.

## What the traces support

When policy was explicit, the model already solved the tested authorization comparisons without
guidance. Guidance influenced investigation organization and invalid-value controls, but did not
improve those classifications. In vulnerable guidance runs, cross-account data was observed before
the invalid-value test, so the bad stopping rule never became decisive. Compensation by the model
does not make that rule correct.

When policy was unavailable, the no-guidance runs read the unavailable-policy record but still
inferred unauthorized access from object ownership and misleading error labels. The primary
guidance run retained uncertainty. That is an observed judgment benefit rather than a gain in
technical discovery. The exploratory guidance text showed the same restraint, but its invalid
JSON cannot count as an automated success. The separately aligned check also retained uncertainty
with a valid structured answer; it is not a replacement or an unbiased repeat of the original arm.

Publication review remains inconsistent. A reviewer demanded policy and attribution conditions
already present in the HTTP draft and demanded an inline internal passage ID despite the frozen
criterion limiting body-placement requirements to explicit requests. After a source-selection
reason changed, the same procedure body was accepted. The confirmed invalid-selector stopping
rule remained. Pipeline approval therefore cannot substitute for technical counterexamples or
independent document judgment.

No new critic stage or semantic acceptance gate was added to obtain these results. Structured
metadata, provenance, formatting and evidence availability remain controller responsibilities;
semantic correctness and materiality still require reasoning and verification.

## Recommended next work

1. Keep the formatting, provenance and local-correction improvements. Keep technique use advisory.
2. Review and validate the corrected HTTP proposal before publishing it. Preserve the historical
   document and its counterexample rather than silently rewriting the experimental subject.
3. Move the next usefulness comparison to the real task-execution path. Freeze model/profile,
   context, tools and fixture-owned ground truth; vary guidance access with paired task runs.
   Validate full assembled production inputs offline before provider calls.
4. Track lookup, delivery, actual application, supported task acceptance and cost separately.
   Controller-correlated task-local observations should establish application; a lookup or a model
   usefulness score alone does not establish benefit.
5. Prefer cases with a genuine information or interpretation gap over more repetitions of a
   generic method the baseline already performs correctly. Include known permission, missing
   permission and legitimate shared-access cases. Preserve failures and incomplete runs.

These are recommendations from the observations, not measured guarantees of improvement. There
is no evidence yet to justify forcing more technique use or expanding generic critic requirements.
A future production-path experiment needs its own bounded protocol; none was started here.

## Full task-controller and real catalog follow-up

The [four-case live follow-up](full-controller-20261115/README.md) used 138 generation requests,
including an eight-request cap-interrupted attempt; 31 of the approved 169 remain unused. The
real embedding preflight indexed 64 revisions and ranked the corrected published HTTP document
first. This establishes retrieval availability, not useful adoption.

Both lookup-enabled cases ended in partial failure without an accepted artifact. One technique
call failed after three research batches on a fixture-specific methodology request; the other
case never called the technique tool and stalled in tool discovery. Neither recorded a use
receipt. Both no-lookup cases published artifacts accepted by the controller, but one lacked a
decisive probe and the other chose the wrong classification despite decisive probes. None passed
the complete independent supported-correct grade.

The practical publication, harness and merge review are complete. Better author output formatting
remains supported by its narrower experiments; better full-controller authorship, increased useful
adoption and improved assessment quality are **not established**. These small synthetic cases also
expose fixture-interface and tool-discovery limitations. The next investigation should inspect
actual bound-tool/catalog consistency and typed fixture parameters, then repeat a small comparison
with reusable domain-level lookup requests. This favors clearer data and deterministic plumbing;
it does not call for more critics or stricter semantic prompts. Do not merge unrelated dirty-tree
work solely on the strength of these experiments.


## November 16 experiment-validity correction

The full-controller fixture inherited reconnaissance lookup filtering and described its input file
as the assessed subject, so the verification method was excluded or semantically mismatched.
Those negative adoption observations do not estimate behavior under a correctly assigned HTTP
verification task. Correct verification context plus an explicit simulated network subject produced
the intended recommendation in one request. Generic bundle delivery also reused the corrected
module document in seven requests without unresolved components. See the
[follow-up](controller-followup-20261116/README.md) for current paired results and the independent
controller repair fix. Earlier author-format results remain separate; no general efficacy claim is
made from the invalid assignment cohorts.


The completed November 16 cohort used 168 generation requests for eight cases. Relevant recommendations
appeared in all three lookup-enabled natural cases, but none retrieved the document. Their label-only
score was 3/3 versus 1/3 without lookup; mechanism review found a correct label with incorrect reasoning,
so this does not establish useful document adoption or a causal efficacy gain. Shared advisory context
produced one correct artifact out of two, with a stale-summary/evaluator-reason inconsistency in that
case. Reliable end-to-end improvement remains unproven. The production catalog-help and explicit
no-repair control fixes passed the final 8,121-test repository run and coverage floors. The
[completed follow-up](controller-followup-20261116/README.md) contains the full matrix, frozen-source
audit and all 446 follow-up request attempts, including retained diagnostics.
