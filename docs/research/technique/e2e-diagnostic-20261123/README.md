# Six paired fixture diagnostics

This experiment measures the handoff from catalog selection to a proposed test, production hypothesis
review contract, actual controlled execution and independent outcome grading. It is diagnostic,
not deployment approval. Each of six cases runs baseline and candidate once, with arm order
counterbalanced across cases. The source observations and policy are identical across vulnerable
and enforced variants; implementation truth is not supplied to the model.

HTTP uses an owned loopback redirect helper with allowed and prohibited destinations. Redirects are
never followed. TCP uses an owned loopback record service with two same-role principals and distinct
owned records; status and an error string alone do not reveal whether protected record data is
returned. Filesystem tests read only owned in-root, outside-root and missing markers through a bounded
gateway. Both vulnerable and enforced behavior are independently tested before inference.

The real isolated web-module catalog uses configured embeddings and complete-document selection,
including request preparation, compatibility and abstraction preservation when rewritten. No technique research or authorship is started.
Baseline selection receives reusable methodology only; candidate additionally receives task-local
context. Each arm authors one future test using the existing Hypothesis schema. The real controller
assembles its bound review input and native output schema; canonical review validation remains in
force. One proposal correction is permitted. Accepted proposals proceed to the native SDK tool
investigation loop, using only fixture tools, then structured classification. Unresolved reviews do
not proceed to execution. Independent Python grading requires correct classification and cited policy,
allowed baseline and boundary variation. Inert control execution is separately observed.

Whole-operation planning/scheduling, production acceptance-ledger transitions, automatic trigger
matching/delivery and fresh technique-document authorship are excluded. The harness reuses tested
controller fixture construction rather than claiming to run a complete production operation. Saved
structured records and isolated catalog SQLite receipts provide stage provenance; receipts and
feedback scores are not useful-adoption proof. These six pairs provide diagnostic evidence, not a
population accuracy estimate.

Each trial is capped at 30 sequential generation requests; all twelve trials share 360 requests.
Existing result files are never rerun. Budget failures remain recorded rather than being silently
restarted. New model calls are authorized under the user's standing allowance. Inputs, schemas,
selection events, stage request counts, delivered documents, proposals, reviews, actual observations
and outcomes remain under `outputs/technique_review_trials/e2e-diagnostic-20261123/`. The protocol is
frozen before live model calls. No production code, operation, source document version or global
library is changed by the experiment.

## Readiness and live start

21 readiness tests passed, including all twelve scripted arm/fixture handoffs, actual loopback and
filesystem behavior, production canonical review validation, negative grading, failure persistence,
resume behavior and request-cap enforcement before network calls. These scripted tests establish
contract readiness, not semantic quality. Ruff and whitespace checks passed.

The isolated catalog initialized with 64 module revisions. Its revision/content snapshot, research
source hashes, production source hashes and current source diff are saved before trial inference.
Generation request accounting has started in selection. Each role invocation uses a fresh native
SDK agent. Proposal/execution use the specialist role runner rather than the complete operation
runtime; review uses the production evaluator system and bound canonical contract. Artifact-reader
recovery loops and production ledger/state transitions are not exercised. These limitations matter
when translating the results into production expectations.

Selected guidance is recorded as an isolated delivery receipt before it reaches the proposal input.
The outcome grade uses actual fixture observations and policy, never the receipt, selected title,
feedback score, success code or artifact readability as proof of a security effect. Source-policy
and target fixture paths use case indices rather than vulnerable/enforced labels in model-visible
inputs. Results will be adjudicated after all attempts, with completed failures preserved.

## Completed diagnostic

All twelve attempts completed, using 142 of 360 available generation requests. Both arms delivered
relevant existing guidance in 6/6 cases, selected the same revision in every pair, passed initial
proposal review without a repair, executed allowed/boundary/inert controls, and produced 6/6 supported
correct classifications. HTTP redirect, TCP protected record and filesystem containment effects were
verified from actual owned fixture observations, including enforced variants. Native structured
finalization accounted for 60 requests; 82 normal tool-investigation requests preceded those finals.
The presence of an unconstrained investigation turn is not a structured-output failure.

| Measure | Baseline | Candidate |
| --- | ---: | ---: |
| Supported correct classifications | 6/6 | 6/6 |
| Guidance delivered | 6/6 | 6/6 |
| Inert controls executed | 6/6 | 6/6 |
| Proposal repairs | 0 | 0 |
| Selection requests | 12 | 12 |
| Proposal requests | 6 | 6 |
| Review requests | 6 | 6 |
| Execution requests | 51 | 43 |
| Total generation requests | 75 | 67 |

The eight-request difference occurred only in filesystem execution, where the candidate batched
context/probe calls more aggressively. Both arms otherwise performed the decisive checks. One
counterbalanced run per case cannot establish causal or expected savings; do not attribute it to the
selection/review changes. There was no no-guidance arm, and guide-consistent controls are not proof
that guidance caused the behavior. Fresh technique-document authorship was not exercised.

Inspection of all twelve accepted proposals and final execution explanations found imperfections
that a completed fixture grade does not erase. The vulnerable TCP candidate proposal listed permitted
baselines among positive expectations and allowed an unauthorized-access error as a positive
alternative; the reviewer marked discrimination adequate. The executor correctly required actual
cross-principal protected record data and cited the ownership policy and controls. Some filesystem
proposals mentioned an ordinary application route absent from their interface, and redirect baseline
wording sometimes assumed same-origin rather than the exact allowlist. Executors adapted to the
actual fixtures and did not perform those irrelevant operations. See `adjudication.json`.

The practical conclusion is narrower than a production improvement claim: the core selected-guide →
proposal → review → execution handoff can produce meaningful tests and supported outcomes in these
owned fixtures. The candidate demonstrated no incremental correctness, delivery or useful-adoption
increase over baseline. It does not override earlier failed promotion gates. Nothing was deployed.

The next discriminating diagnostic should exercise automatic trigger/lead matching and delivery from
ambiguous assigned observations, particularly wrong-method leads with similar evidence shape. This
run supplied precise methodology requests, so it bypassed the stage implicated in the real operation's
poor selections. Do not add another critic or tighten proposal acceptance based solely on the TCP
wording issue: execution judgment recovered correctly here, matching the intended advisory workflow.

## Validation

21 fixture/pipeline readiness tests, Ruff and whitespace checks passed. The final post-presentation-
rollback production coverage suite passed **8,381 tests**, with 47 skips and 89 deselections; all changed
production Python files meet the 80% line/branch floor. This diagnostic added research code only and
changed no production behavior. Earlier experiments, code snapshots and failed gates remain intact.


A subsequent [automatic matching diagnostic](../automatic-matching-20261123/README.md) exercised the
previously excluded lead stage. It found appropriate shared ranked leads, but the added per-document
task-fit veto unnecessarily refused thin-input conditional guidance. That extra veto has now been
removed from runtime; this completed end-to-end study retains its original tested implementation and
results. Its `select_existing` path does not invoke multi-component bundle planning/phase alignment.
