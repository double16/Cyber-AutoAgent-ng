# Automatic matching and delivery diagnostic

Ten cases exercise the actual batched trigger matcher and automatic delivery boundary from assigned
and shared observations rather than precise methodology requests. Six cover browser navigation,
server-side preview retrieval, DOM rendering, signed session verification, TCP record ownership and
filesystem containment. Two controls expose no recorded boundary despite unrelated shared features.
Two thin-input cases cover an opaque navigation helper assigned redirect/URL-retrieval investigation
and a legitimately assigned authentication helper with unrecorded inputs. The latter is a positive
reuse control for the captured generic authentication guide; it must not be categorically rejected.

Each case uses real catalog embedding retrieval, module signal adapters and a fresh native ranked
matching decision. The exact ranked leads are then shared by the two arms, preventing stochastic
matching differences from masquerading as downstream selection improvement. Baseline uses the old
first-lead methodology-only decision; candidate uses task-local selection across up to three leads.
Both use the current delivery receipt, lifecycle and capacity checks with a real SDK Agent and its
configured context/output capacity. No executor generation occurs after injection in this diagnostic.

The isolated catalog imports the module's 64 documents and two captured generated guides that
previously competed for the navigation task: authentication from minimal evidence and server-side
request destination boundaries. Authored fields/body are retained while historical lifecycle, scores
and use feedback are stripped. These replay imports neither change nor assert current eligibility in
the active operation's library. Captured source hashes and normalization provenance are retained.
No active operation database or global catalog is written.

The frozen case file records expected specialist documents as a retrieval/ranking diagnostic only.
A different broad document is not automatically wrong: adjudication must inspect whether an adaptable
procedure serves the assigned work. Unknown target prerequisites remain conditional. Empty matching
is distinguished from unavailable/invalid matching. No stricter critic or acceptance schema is added.

The study has a shared 512-request cap, four requests per matching unit and thirty per selection arm.
Arm order is counterbalanced. Completed results are never selectively rerun. No target requests,
new document authorship, operation scheduling or executor-usefulness claims are part of this study.

## Readiness and live start

Six contract-readiness tests passed before inference. They check ten-case coverage, positive and
negative controls, captured document normalization, real matching handoff, receipt persistence, arm
context separation, resume behavior, and valid empty versus invalid matching. Ruff and whitespace
checks passed. The live catalog import and matching run have started under the frozen protocol.
Research/production source hashes and the source diff are retained in the isolated output root.

A delivery outcome with `status=finished` means the hook returned; it does not by itself mean a valid
semantic selection was made. Adjudication must inspect the retained delivery events: unavailable,
capacity-deferred or invalid selection is neither an empty semantic decision nor a negative-control
success. A guide outside the expected-specialist list also requires procedure-level inspection rather
than automatic rejection by title. No useful-adoption inference will be made from injection receipts.

## Completed comparison and decision

The ten matching units completed in ten native generation requests. All eight positive cases had
relevant leads; both no-boundary controls had no leads. There were no matching, selection-runtime or
capacity failures. Baseline delivered useful guidance in 8/8 positive cases and correctly omitted
both negative controls, using 17 selection requests. The task-veto candidate delivered 7/8 positives
and omitted both controls, using 26 selection requests. Total study use was 53 requests.

A different-than-expected title was not treated as a failure. The HTML/CSS injection guide supplied
plain-marker, DOM-location, inert-markup and interpretation controls useful for the map-title task,
with script execution explicitly separated. The captured minimal-evidence authentication guide was
correctly reused for the legitimately assigned authentication helper. Generic documents were not
categorically refused.

The only candidate miss was opaque-navigation. Matching ranked redirect guidance first. Its document
review found the requested capability conditional, but the separate task-relevance decision refused
it because navigation prerequisites were unobserved and the wider task also asked about server-side
URL retrieval. Thus a guide that usefully covered one requested component was vetoed for lacking
whole-task coverage/confirmed prerequisites. The candidate scanned other unrelated documents without
delivery. Baseline correctly delivered the conditional redirect guidance.

The runtime has been simplified based on this failure. Task relevance stays in the existing batched
matcher, while document selection assesses methodological capability coverage. The per-document
task-relevance field and whole-task veto were removed. No stricter prompt or critic was introduced.
The bounded three-lead fallback and shared review cache remain. Pending delivery bindings increment
to invalidate prior decisions; delivered snapshots remain historical. Lookup/generation receives
methodology-only context, preserving unknown prerequisites and useful subsets of larger tasks.
Public tools, document versions and database schemas are unchanged.

The tested prior service, delivery and selection-schema sources are archived as `*.tested.txt`.
Historical selection output schemas are preserved separately in the earlier study's
`selection_review_snapshot.py`, so immutable input/schema checks do not silently adopt the new
runtime contract. Historical study drivers need their recorded runtime snapshots for new inference;
their completed results are not rerun or relabeled.

A fresh whole-corpus recheck of the simplified path is running across all ten frozen matcher decisions,
not merely the failed case. It uses a copied isolated catalog, new task/receipt scopes, a separate
160-request cap and unchanged task observations. This is a single-arm compatibility recheck against
known controls, not a new paired causal estimate. Its protocol is `simplified-protocol.json`.

69 focused/research tests passed after the removal; the focused delivery/cache suite then passed 57
tests, and the additional shared-review-cache test passed in an eleven-test cache run. Ruff and diff
checks pass. Full repository coverage is running on the simplified production code. No deployment
or library mutation occurred, and this delivery-only diagnostic does not establish useful executor
adoption or improved document authorship.


## Simplified path verified

The fresh single-arm whole-corpus check completed in **18 requests** (160 allowed). It delivered
useful guidance for **8/8 positive cases**, omitted guidance for **2/2 negative controls**, and had
**zero runtime or capacity failures**. All selected revisions matched the original baseline's choices,
including the captured generic authentication guide and broad HTML/CSS guide. The opaque navigation
case again received conditional redirect guidance in two requests. These results restore the original
baseline's behavior while retaining bounded fallback; they do not establish an improvement over that
baseline or increased executor adoption. See `simplified-results.json`.

Final production verification passed: **8,378 tests**, 47 skips and 89 deselections. Every changed
production Python file passed the 80% line and branch floors. The additional review-cache-sharing
test, added after full-suite collection, passed in the eleven-test cache run. Ruff and whitespace
checks passed. No model experiment remains running and no deployment occurred. The simplification
is ready for code review; assessing real-operation adoption still requires observation of automatic
selection and downstream tests in an authorized continuation.
